  │  ┌─ .tabs  width:100%; max-width:400px ─────┐          │

  │      ▲                                    ▲   ▲        │

  │                                    clipped, reachable  │
  │                                    only by scrolling   │
  └────────────────────────────────────────────────────────┘


One gotcha worth knowing: max-width: 50% resolves against the containing block. If the parent is a flex item or has no definite width,

## A bug in the current CSS

Tabs.css today:

css
.tabs {
    height: 27px;
    overflow: hidden;          /* ← no scrollbar */
}
.tabs:hover, .tabs:active, .tabs:focus {
    overflow-x: auto;          /* ← scrollbar appears only on hover */
}


Two problems for this feature:

The scrollbar only exists on hover, which is the opposite of what you asked for. Note that overflow: hidden does not block
programmatic scrolling — scrollLeft still works — so scroll-into-view would function, but the user gets no visible affordance and can
't scroll by hand.

Toggling overflow on hover reflows the box. With height: 27px fixed and .tab { height: 100% }, a classic ~15px horizontal scrollbar
eats over half the content box, so tabs visibly squash when the pointer enters. Fix by making the scrollbar permanent and thin:

css
.tabs {
    position: relative;       /* also useful for the measuring math */
    overflow-x: auto;
    overflow-y: hidden;
    scrollbar-width: thin;
    scroll-behavior: smooth;  /* applies to programmatic scrollLeft too */
    min-height: 27px;         /* replace fixed height so the bar fits */
}
@media (prefers-reduced-motion: reduce) {
    .tabs { scroll-behavior: auto; }
}


scroll-behavior: smooth in CSS also governs scrollLeft assignments from JS, so smooth animation needs zero JavaScript — and the
reduced-motion query handles accessibility for free.

# Part 2 — scrolling the active tab into view

## Don't use scrollIntoView()

The obvious answer is tab.scrollIntoView({ inline: "nearest" }). I'd avoid it:

   ┌─ the page (scrollable) ─────────────────┐
   │  ...lots of content above...            │
   │  ┌─ .tabs (scrollable) ──────────┐      │
   │  │ t1 │ t2 │ t3 │ ...            │      │
   │  └───────────────────────────────┘      │
   └─────────────────────────────────────────┘

   scrollIntoView scrolls EVERY scrollable ancestor, not just .tabs
   → selecting a tab can jump the whole page


block: "nearest" reduces it but doesn't contain it. Writing container.scrollLeft directly touches exactly one element and nothing
else. It's also trivially cancellable and testable.

## The arithmetic

Everything happens in one coordinate space: pixels from the container's left content edge.

  content space (0 … scrollWidth)
  0                                                          scrollWidth
  ├─────────────────────────────────────────────────────────────────┤
  │ t1 │ t2 │ t3 │ t4 │ t5 │ t6 │ t7 │ t8 │ t9 │t10 │t11 │t12 │t13 │
                 ╞═══════════ visible ═══════════╡
                 ▲                               ▲
           scrollLeft            scrollLeft + clientWidth


Three cases, and the third is the important one:

  CASE A — tab starts before the viewport         → scroll left
     ┌────┐
     │ t2 │      ╞═════════ visible ═════════╡
     └────┘
     scrollLeft += (tabStart − viewStart) − margin

  CASE B — tab ends after the viewport            → scroll right
                 ╞═════════ visible ═════════╡      ┌────┐
                                                    │ t12│
                                                    └────┘
     scrollLeft += (tabEnd − viewEnd) + margin

  CASE C — already fully visible                  → DO NOTHING
                 ╞═════════ visible ═════════╡
                       ┌────┐
                       │ t7 │
                       └────┘


Case C makes the operation minimal and idempotent — the same behaviour as inline: "nearest", and the reason selecting an already-
visible tab doesn't cause a jarring re-centre. The small margin (say 8px) leaves a sliver of the neighbouring tab showing, which both
looks less clipped and hints that there's more content.

Measure with rectangles rather than offsetLeft:

   delta = tabRect.left − containerRect.left − container.clientLeft
   visible region is [0, container.clientWidth]


offsetLeft is relative to the nearest positioned ancestor, so it silently breaks unless .tabs is position: relative. The rect-delta
version has no such dependency, and it already accounts for the current scroll position. clientLeft subtracts the container's border
so the comparison against clientWidth is exact.

## Timing — the first real trap

  useEffect  (WRONG)
  render ─▶ DOM commit ─▶ ▓ PAINT ▓ ─▶ measure ─▶ set scrollLeft ─▶ ▓ PAINT ▓
                              │                                        │
                              └─ user sees the OLD scroll position ─────┘
                                        = a visible flash

  useLayoutEffect  (RIGHT)
  render ─▶ DOM commit ─▶ measure ─▶ set scrollLeft ─▶ ▓ PAINT ▓
                                                          │
                                            user only ever sees the
                                            correct position


Layout effects run after React commits the DOM but before the browser paints, so the scroll correction lands in the same frame. This
matters most on first mount: if activeTabId is the 20th tab, useEffect would paint tab 1 and then snap.

## When to run it — the actual hard part

This is the part I'd think about longest, because the failure mode is subtle: an over-eager implementation fights the user.

If you scroll manually to inspect tab 12 while tab 1 is active, and any unrelated re-render re-asserts the scroll, the view yanks
back to tab 1. That rules out the tempting "just run the check on every render, it's idempotent" approach.

So the trigger set has to be deliberate:

  trigger                              detected by        re-scroll?
  ──────────────────────────────────────────────────────────────────
  active tab changed                   activeId dep         YES
  active tab moved (reorder / close    activeIndex dep      YES
    of an earlier tab)
  container resized (%, vw, responsive) ResizeObserver      YES*
  user scrolled by hand                — nothing —          NO
  unrelated parent re-render           — nothing —          NO
  drag in progress                     isDragging guard     NO


Two of those fall out of work already done:

- **activeIndex** is already computed for free during the existing single forEachTab traversal — we added it for onActiveTabChange.
It's a sound proxy for "the active tab's horizontal position changed": closing or reordering an earlier tab changes it, while changes
after the active tab don't move it and correctly trigger nothing.
- **isDragging** is already exposed by useDragReorder. Without this guard, dragging the active tab would trigger scroll corrections
mid-drag and fight the pointer.

The * on resize is a genuine judgement call: re-asserting on resize can also yank a user who has scrolled away. The compromise is to
remember whether the active tab was visible before the resize and only re-assert if it was. Cheap to do, and I'd default to it.

"Why React but no component libraries?"

I took exactly one dependency for rendering and none for components, and the dividing line is a single question: does this dictate my
data shape or my design? React dictates neither — it gives me reconciliation and a component model and asks for nothing back. A
component library dictates at least one, usually both.

Concretely, every grid library I looked at requires rows: T[] in its public API. You materialize your data into their shape and hand
it over. My components require operations instead: the tab bar takes a single-pass iterator, forEachTab(data, visit), and the grid
takes random access, getCell(data, row, col). The data itself is an opaque generic. So they work directly over a tree, a linked list,
or a remote source with no adapter layer — and the tab bar builds no projection array at all, which matters because indexed access
over a linked list would be O(n²). The grid reads only the cells it renders, so cost scales with what's on screen rather than with
the dataset. That's dependency inversion, and it's the one thing a library structurally cannot concede, because a fixed data shape is
what its API is made of.

I should address the obvious counter: headless libraries solve the styling half of this. TanStack Table ships zero markup and zero
styles, and React Aria does the same for behaviour. So "I didn't want their design taste" isn't a real argument — but the data
contract still is, and for a bookkeeping app there's a licensing dimension too: AG Grid's advanced features are commercial, and
Handsontable requires a paid licence for commercial use.

The payoff showed up when I moved the grid from divs to a native <table>. I'd written 30 behaviour tests against the old markup,
phrased only in ARIA roles and user actions, and all 30 passed unchanged against the new elements. Swapping the entire DOM
representation touched no orchestration code, because the host owns the data shape and the coordinator never knows which element
anything is.

Now the cost, because it wasn't free. My tab bar puts 33 tab stops on the page with 17 tabs and has no arrow-key navigation. The grid
has cells carrying a roving tabIndex that nothing ever focuses, no aria-rowcount/aria-colcount, and controlled selection with no
write half. React Aria would have given me correct ARIA and focus management on day one. I accepted that trade for control over the
data contract and the interaction model, and every gap is written down in the module READMEs rather than waiting to be discovered. I'
m carrying the maintenance burden deliberately: 276 tests, and I verified each one bites by sabotaging the implementation and
checking that the right tests fail.

Where would I take the dependency? A date picker, a rich-text editor, a charting library — standard widgets with a huge correctness
surface and no design differentiation to protect. I built these two because the tab bar's data model and the grid's access pattern are
the design.

For the C++ version, same principle, different runtime. I'd keep React's declarative authoring model, because that's what makes UI
code readable, but not its runtime strategy. Allocating a fresh tree every render and diffing it is allocation-heavy and pointer-
chasing — close to the opposite of what you want when you care about cache behaviour. So I'd pair React-like authoring with fine-
grained invalidation over flat, contiguous storage: touch only what changed. That tension between the authoring model and the
reconciliation strategy is the interesting part of the problem.

## 1. Clipping as you pan away

You don't need any code for this. It falls out of where the overlay lives.

.grid is the scroll container (overflow: auto) and will be the overlay's containing block (position: relative). When both are true,
the browser clips the absolutely-positioned overlay to .grid's box. So:

pan away  ->  less and less of the editor is drawn
           ->  one character's worth left, one character shows
           ->  zero left, nothing shows
pan back  ->  it reappears, progressively


That's the browser's own clipping, not logic you maintain. It's continuous by nature, so "as long as one character fits, show it"
needs no threshold and no special case — there's nothing to get wrong.

The one thing this does depend on: the overlay must be a child of .grid, not of .spreadsheet. If it sat outside the scroll container

The sub-decision inside this. My width rule clamps against the right edge: width = min(cellRight, viewportRight) - cellLeft. Should it

stays wrapped exactly as it was, and you see progressively less of it. Panning left still rewraps, which is the transition your own
diagrams show and want.
