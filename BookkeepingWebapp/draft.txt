Applied as an inline style on the container in Tabs.tsx. Percentages, vw, calc(), clamp() all come along for free because CSS

  ┌─ parent ───────────────────────────────────────────────┐
  │                                                        │
  │  ┌─ .tabs  width:100%; max-width:400px ─────┐          │
  │  │ overflow-x:auto  ← the scroll viewport   │          │
  │  ╞══════════════════════════════════════════╡          │
  │  │ t1 │ t2 │ t3 │ t4 │ t5 │ t6 ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ t7…t13 │
  │  └──────────────────────────────────────────┘          │
  │      ▲                                    ▲   ▲        │
  │      └── clientWidth (what you see) ──────┘   │        │
  │                                    clipped, reachable  │
  │                                    only by scrolling   │
  └────────────────────────────────────────────────────────┘


One gotcha worth knowing: max-width: 50% resolves against the containing block. If the parent is a flex item or has no definite width,
a percentage can collapse or behave unexpectedly. Nothing we can fix in the component — just a documentation note.

## A bug in the current CSS

Tabs.css today:

css
.tabs {
    height: 27px;
    overflow: hidden;          /* ← no scrollbar */
}
.tabs:hover, .tabs:active, .tabs:focus {
    overflow-x: auto;          /* ← scrollbar appears only on hover */
}


Two problems for this feature:

The scrollbar only exists on hover, which is the opposite of what you asked for. Note that overflow: hidden does not block
programmatic scrolling — scrollLeft still works — so scroll-into-view would function, but the user gets no visible affordance and can
't scroll by hand.

Toggling overflow on hover reflows the box. With height: 27px fixed and .tab { height: 100% }, a classic ~15px horizontal scrollbar
eats over half the content box, so tabs visibly squash when the pointer enters. Fix by making the scrollbar permanent and thin:

css
.tabs {
    position: relative;       /* also useful for the measuring math */
    overflow-x: auto;
    overflow-y: hidden;
    scrollbar-width: thin;
    scroll-behavior: smooth;  /* applies to programmatic scrollLeft too */
    min-height: 27px;         /* replace fixed height so the bar fits */
}
@media (prefers-reduced-motion: reduce) {
    .tabs { scroll-behavior: auto; }
}


scroll-behavior: smooth in CSS also governs scrollLeft assignments from JS, so smooth animation needs zero JavaScript — and the
reduced-motion query handles accessibility for free.

# Part 2 — scrolling the active tab into view

## Don't use scrollIntoView()

The obvious answer is tab.scrollIntoView({ inline: "nearest" }). I'd avoid it:

   ┌─ the page (scrollable) ─────────────────┐
   │  ...lots of content above...            │
   │  ┌─ .tabs (scrollable) ──────────┐      │
   │  │ t1 │ t2 │ t3 │ ...            │      │
   │  └───────────────────────────────┘      │
   └─────────────────────────────────────────┘

   scrollIntoView scrolls EVERY scrollable ancestor, not just .tabs
   → selecting a tab can jump the whole page


block: "nearest" reduces it but doesn't contain it. Writing container.scrollLeft directly touches exactly one element and nothing
else. It's also trivially cancellable and testable.

## The arithmetic

Everything happens in one coordinate space: pixels from the container's left content edge.

  content space (0 … scrollWidth)
  0                                                          scrollWidth
  ├─────────────────────────────────────────────────────────────────┤
  │ t1 │ t2 │ t3 │ t4 │ t5 │ t6 │ t7 │ t8 │ t9 │t10 │t11 │t12 │t13 │
                 ╞═══════════ visible ═══════════╡
                 ▲                               ▲
           scrollLeft            scrollLeft + clientWidth


Three cases, and the third is the important one:

  CASE A — tab starts before the viewport         → scroll left
     ┌────┐
     │ t2 │      ╞═════════ visible ═════════╡
     └────┘
     scrollLeft += (tabStart − viewStart) − margin

  CASE B — tab ends after the viewport            → scroll right
                 ╞═════════ visible ═════════╡      ┌────┐
                                                    │ t12│
                                                    └────┘
     scrollLeft += (tabEnd − viewEnd) + margin

  CASE C — already fully visible                  → DO NOTHING
                 ╞═════════ visible ═════════╡
                       ┌────┐
                       │ t7 │
                       └────┘


Case C makes the operation minimal and idempotent — the same behaviour as inline: "nearest", and the reason selecting an already-
visible tab doesn't cause a jarring re-centre. The small margin (say 8px) leaves a sliver of the neighbouring tab showing, which both
looks less clipped and hints that there's more content.

Measure with rectangles rather than offsetLeft:

   delta = tabRect.left − containerRect.left − container.clientLeft
   visible region is [0, container.clientWidth]


offsetLeft is relative to the nearest positioned ancestor, so it silently breaks unless .tabs is position: relative. The rect-delta
version has no such dependency, and it already accounts for the current scroll position. clientLeft subtracts the container's border
so the comparison against clientWidth is exact.

## Timing — the first real trap

  useEffect  (WRONG)
  render ─▶ DOM commit ─▶ ▓ PAINT ▓ ─▶ measure ─▶ set scrollLeft ─▶ ▓ PAINT ▓
                              │                                        │
                              └─ user sees the OLD scroll position ─────┘
                                        = a visible flash

  useLayoutEffect  (RIGHT)
  render ─▶ DOM commit ─▶ measure ─▶ set scrollLeft ─▶ ▓ PAINT ▓
                                                          │
                                            user only ever sees the
                                            correct position


Layout effects run after React commits the DOM but before the browser paints, so the scroll correction lands in the same frame. This
matters most on first mount: if activeTabId is the 20th tab, useEffect would paint tab 1 and then snap.

## When to run it — the actual hard part

This is the part I'd think about longest, because the failure mode is subtle: an over-eager implementation fights the user.

If you scroll manually to inspect tab 12 while tab 1 is active, and any unrelated re-render re-asserts the scroll, the view yanks
back to tab 1. That rules out the tempting "just run the check on every render, it's idempotent" approach.

So the trigger set has to be deliberate:

  trigger                              detected by        re-scroll?
  ──────────────────────────────────────────────────────────────────
  active tab changed                   activeId dep         YES
  active tab moved (reorder / close    activeIndex dep      YES
    of an earlier tab)
  container resized (%, vw, responsive) ResizeObserver      YES*
  user scrolled by hand                — nothing —          NO
  unrelated parent re-render           — nothing —          NO
  drag in progress                     isDragging guard     NO


Two of those fall out of work already done:

- **activeIndex** is already computed for free during the existing single forEachTab traversal — we added it for onActiveTabChange.
It's a sound proxy for "the active tab's horizontal position changed": closing or reordering an earlier tab changes it, while changes
after the active tab don't move it and correctly trigger nothing.
- **isDragging** is already exposed by useDragReorder. Without this guard, dragging the active tab would trigger scroll corrections
mid-drag and fight the pointer.

The * on resize is a genuine judgement call: re-asserting on resize can also yank a user who has scrolled away. The compromise is to
remember whether the active tab was visible before the resize and only re-assert if it was. Cheap to do, and I'd default to it.

## Finding the active tab's DOM node

The coordinator builds tabElements but holds no DOM references, so there are three ways in:

  (a) query the container      container.querySelector('[aria-selected="true"]')

  (c) let each Tab scroll itself   useLayoutEffect inside Tab, keyed on `active`

"Why React but no component libraries?"

I took exactly one dependency for rendering and none for components, and the dividing line is a single question: does this dictate my
data shape or my design? React dictates neither — it gives me reconciliation and a component model and asks for nothing back. A
component library dictates at least one, usually both.

Concretely, every grid library I looked at requires rows: T[] in its public API. You materialize your data into their shape and hand
it over. My components require operations instead: the tab bar takes a single-pass iterator, forEachTab(data, visit), and the grid
takes random access, getCell(data, row, col). The data itself is an opaque generic. So they work directly over a tree, a linked list,
or a remote source with no adapter layer — and the tab bar builds no projection array at all, which matters because indexed access
over a linked list would be O(n²). The grid reads only the cells it renders, so cost scales with what's on screen rather than with
the dataset. That's dependency inversion, and it's the one thing a library structurally cannot concede, because a fixed data shape is
what its API is made of.

I should address the obvious counter: headless libraries solve the styling half of this. TanStack Table ships zero markup and zero
styles, and React Aria does the same for behaviour. So "I didn't want their design taste" isn't a real argument — but the data
contract still is, and for a bookkeeping app there's a licensing dimension too: AG Grid's advanced features are commercial, and
Handsontable requires a paid licence for commercial use.

The payoff showed up when I moved the grid from divs to a native <table>. I'd written 30 behaviour tests against the old markup,
phrased only in ARIA roles and user actions, and all 30 passed unchanged against the new elements. Swapping the entire DOM
representation touched no orchestration code, because the host owns the data shape and the coordinator never knows which element
anything is.

Now the cost, because it wasn't free. My tab bar puts 33 tab stops on the page with 17 tabs and has no arrow-key navigation. The grid
has cells carrying a roving tabIndex that nothing ever focuses, no aria-rowcount/aria-colcount, and controlled selection with no
write half. React Aria would have given me correct ARIA and focus management on day one. I accepted that trade for control over the
data contract and the interaction model, and every gap is written down in the module READMEs rather than waiting to be discovered. I'
m carrying the maintenance burden deliberately: 276 tests, and I verified each one bites by sabotaging the implementation and
checking that the right tests fail.

Where would I take the dependency? A date picker, a rich-text editor, a charting library — standard widgets with a huge correctness
surface and no design differentiation to protect. I built these two because the tab bar's data model and the grid's access pattern are
the design.

For the C++ version, same principle, different runtime. I'd keep React's declarative authoring model, because that's what makes UI
code readable, but not its runtime strategy. Allocating a fresh tree every render and diffing it is allocation-heavy and pointer-
chasing — close to the opposite of what you want when you care about cache behaviour. So I'd pair React-like authoring with fine-
grained invalidation over flat, contiguous storage: touch only what changed. That tension between the authoring model and the
reconciliation strategy is the interesting part of the problem.

Implement selection range state:

That makes sense. The confusing part is that you are trying to satisfy two requirements that pull in opposite directions:

The selection must be accessible outside the rendering layer.
Changing the selection should rerender only the small selection overlay.

The intuitive solution is: the selection is kept in a small shared object, and the overlay listens to that object. React does not need to own every piece of application state through useState.

Think of it as a radio station

The selection controller is a small radio station:

Selection controller
    current selection: A1:C4


Different code can interact with it:

Mouse interaction → changes selection
Delete rows      → changes selection
Undo             → changes selection
Sheet replacement → changes selection


The selection overlay is the only React component tuned to that station:

Selection controller broadcasts a change
                  ↓
Selection overlay hears it
                  ↓
Selection overlay rerenders


The cell layer is not listening, so it does not rerender.

There is only one selection

There are not two synchronized selection values.

SelectionController
└── contains the one authoritative selection

SelectionLayer
└── displays that selection


The overlay does not own another copy. It asks the controller for the current value.

Start with this small controller

Forget generic types, undo, structural transformations, and optimizations for the moment:

interface CellPosition {
    row: number;
    column: number;
}

interface SelectionRange {
    anchor: CellPosition;
    focus: CellPosition;
}

class SelectionController {
    private selection: SelectionRange = {
        anchor: { row: 0, column: 0 },
        focus: { row: 0, column: 0 },
    };

    private listeners = new Set<() => void>();

    getSelection = (): SelectionRange => {
        return this.selection;
    };

    setSelection(selection: SelectionRange): void {
        this.selection = selection;

        for (const listener of this.listeners) {
            listener();
        }
    }

    subscribe = (listener: () => void): (() => void) => {
        this.listeners.add(listener);

        return () => {
            this.listeners.delete(listener);
        };

(using useSyncExternalStore)

Yes. useSyncExternalStore is a React hook intended for exactly this situation:

The state is stored outside React, but a React component needs to rerender when that external state changes.

It takes two essential functions:

useSyncExternalStore(subscribe, getSnapshot)

subscribe tells React how to listen for changes.
getSnapshot tells React how to read the current value.
Minimal example
1. An ordinary TypeScript store owns the selection
export interface CellPosition {
    row: number;
    column: number;
}

export interface SelectionRange {
    anchor: CellPosition;
    focus: CellPosition;
}

export class SelectionStore {
    private selection: SelectionRange = {
        anchor: { row: 0, column: 0 },
        focus: { row: 0, column: 0 },
    };

    private readonly listeners = new Set<() => void>();

    getSnapshot = (): SelectionRange => {
        return this.selection;
    };

    subscribe = (listener: () => void): (() => void) => {
        this.listeners.add(listener);

        return () => {
            this.listeners.delete(listener);
        };
    };

    setSelection(next: SelectionRange): void {
        if (
            this.selection.anchor.row === next.anchor.row &&
            this.selection.anchor.column === next.anchor.column &&
            this.selection.focus.row === next.focus.row &&
            this.selection.focus.column === next.focus.column
        ) {
            return;
        }

        this.selection = next;

        for (const listener of this.listeners) {
            listener();
        }
    }
}


There is only one selection, stored inside SelectionStore.

2. The overlay subscribes to it

Two important rules
getSnapshot() must be stable

It should return the same object until the selection changes:

getSnapshot = () => this.selection;


Do not return a newly copied object:

// Wrong: appears changed every time React reads it.
getSnapshot = () => ({
    ...this.selection,
});


React compares snapshots using Object.is. If getSnapshot() always creates a new object, React can repeatedly detect changes even though the logical selection stayed the same.

Methods passed to the hook must remain bound

Using arrow functions ensures that this still refers to the store:

getSnapshot = () => this.selection;

subscribe = listener => {
    // ...
};


Ordinary class methods would require binding:

this.subscribe = this.subscribe.bind(this);


Arrow properties are simpler here.

What the axes represent

You need two mappings:

row index    → content-space Y position and height
column index → content-space X position and width


For example:

interface AxisLayout {
    getStart(index: number): number;
    getSize(index: number): number;
    findIndexAt(position: number): number;
    readonly totalSize: number;
}


Then the complete layout is:

interface TableLayout {
    rows: AxisLayout;
    columns: AxisLayout;

    readonly totalWidth: number;
    readonly totalHeight: number;
}


The two directions are important.

Rendering
row/column index → pixel position

const y = layout.rows.getStart(row);

const width = layout.columns.getSize(column);
const height = layout.rows.getSize(row);

Hit testing
pointer position → row/column index

const column = layout.columns.findIndexAt(contentX);
const row = layout.rows.findIndexAt(contentY);


The cell layer, selection layer and pointer interaction logic all use the same layout object.

Do not rebuild the position cache after every selection change

This is the critical answer to your question.

A selection change does not change:

row positions;
column positions;
row heights;
column widths;
total content size.

Therefore, it must not rebuild the axis layout.

Your dependencies should look like this:

Data structure/order/size change
        ↓
Axis layout may change

Selection change
        ↓
Axis layout unchanged
        ↓
Only selection rectangle recalculated


The layout should be persistent across renders, or memoized from only the values that affect geometry.

For example:

const layout = useMemo(
    () =>
        createTableLayout({
            rowCount: getRowCount(data),
            columnCount: getColumnCount(data),
            getRowHeight,
            getColumnWidth,
        }),
    [
        dataLayoutRevision,
        getRowHeight,
        getColumnWidth,
    ],
);


However, be careful with using data itself as the dependency:

// Potentially rebuilds layout after every cell-value edit.

Editing a cell value might create a new data object even though geometry did not change.

A better dependency is a dedicated layout or projection revision:

const layout = useMemo(
    () =>
        createTableLayout({
            rowCount,
            columnCount,
            getRowHeight,
            getColumnWidth,
        }),
    [
        layoutRevision,
        rowCount,
        columnCount,
        getRowHeight,
        getColumnWidth,
    ],
);


A value edit does not change layoutRevision. Inserting a row, resizing a column or expanding a hierarchy node does.

Fixed-size rows and columns need no cache

If every row has the same height and every column has the same width, positions are simple arithmetic:

class FixedAxisLayout implements AxisLayout {
    constructor(
        private readonly count: number,
        private readonly itemSize: number,
    ) {}

    getStart(index: number): number {
        return index * this.itemSize;
    }

    getSize(_index: number): number {
        return this.itemSize;
    }

    findIndexAt(position: number): number {
        return Math.max(
            0,
            Math.min(
                this.count - 1,
                Math.floor(position / this.itemSize),
            ),
        );
    }

    get totalSize(): number {
        return this.count * this.itemSize;
    }
}


Nothing needs rebuilding when the selection changes.

const rowLayout = new FixedAxisLayout(
    rowCount,
    ROW_HEIGHT,
);

const columnLayout = new FixedAxisLayout(
    columnCount,
    COLUMN_WIDTH,
);


The selection rectangle is then cheap to calculate.

Variable sizes may require an index

With variable row heights:

row 0: 24 px
row 1: 30 px
row 2: 50 px
row 3: 24 px


The starting positions are cumulative:

row 0 starts at 0
row 1 starts at 24
row 2 starts at 54
row 3 starts at 104


You could initially use prefix positions:

class VariableAxisLayout implements AxisLayout {
    private readonly starts: number[];

    constructor(private readonly sizes: readonly number[]) {
        this.starts = new Array(sizes.length + 1);
        this.starts[0] = 0;

        for (let index = 0; index < sizes.length; index++) {
            this.starts[index + 1] =
                this.starts[index] + sizes[index];
        }
    }

    getStart(index: number): number {
        return this.starts[index];
    }

    getSize(index: number): number {
        return this.sizes[index];
    }

    findIndexAt(position: number): number {
        let low = 0;
        let high = this.sizes.length;

        while (low < high) {
            const middle = Math.floor(
                (low + high) / 2,
            );

            if (this.starts[middle + 1] <= position) {
                low = middle + 1;
            } else {
                high = middle;
            }
        }

        return Math.min(
            low,
            this.sizes.length - 1,
        );
    }

    get totalSize(): number {
        return this.starts[this.sizes.length];
    }
}


This layout index should be rebuilt or updated only when geometry changes, not when selection changes.

For your fully dependency-inverted design, the renderer need not decide whether this is implemented with:

arithmetic;
a prefix array;
a Fenwick tree;
a segment tree;
an order-statistic tree;
a paged index;
another injected implementation.

It only consumes the AxisLayout capability.

Converting a selection into an overlay rectangle

The overlay uses the shared layout:

function getSelectionRectangle(
    selection: SelectionRange,
    layout: TableLayout,
): Rectangle {
    const firstRow = Math.min(
        selection.anchor.row,
        selection.focus.row,
    );

    const lastRow = Math.max(
        selection.anchor.row,
        selection.focus.row,
    );

    const firstColumn = Math.min(
        selection.anchor.column,
        selection.focus.column,
    );

    const lastColumn = Math.max(
        selection.anchor.column,
        selection.focus.column,
    );

    const top =
        layout.rows.getStart(firstRow);

    const bottom =
        layout.rows.getStart(lastRow) +
        layout.rows.getSize(lastRow);

    const left =
        layout.columns.getStart(firstColumn);

    const right =
        layout.columns.getStart(lastColumn) +
        layout.columns.getSize(lastColumn);

    return {
        x: left,
        y: top,
        width: right - left,
        height: bottom - top,
    };
}

Your accurate final mental model

Your interpretation is almost right. I would phrase it this way:

1. The table has persistent X-axis and Y-axis layout models.

2. Those models map:
   index → pixel position
   pixel position → index

3. The cell layer uses the models to place cells.

4. Pointer handling uses the models to identify the clicked cell.

5. The selection store stores logical cell positions, not pixels.

6. The selection layer uses the same layout models to derive
   the overlay rectangle.

7. Selection changes do not rebuild the axes.

8. Structural or sizing changes update the relevant axes and
   cause the overlay geometry to be derived again.


So no, you should not rebuild the axis-position cache during every selection-layer render. Keep the geometry model stable, change it only when row or column geometry changes, and use it as the common cohesive dependency shared by the cell, interaction, selection, and editing layers.

                <EditBoxLayer
                    controller={editBox}
                    geometry={geometry}
                />
            </div>
        </div>
    );
}


Nothing in this wrapper needs to know:

how many rows are loaded;
whether rows come from an array, AVL tree or B+ tree;
how the visible range is traversed;
whether rendering is memoized per row or per cell;
whether partial loading uses pages or cursors;
how cell invalidation works;
which cell components currently exist.

Those are grid-layer concerns.

What TableGridLayer should own

TableGridLayer is the virtualization and cell-materialization boundary. It should decide:

Which rows and columns intersect the viewport.
How much rendering overscan is needed.
Which loaded windows are missing.
When more data should be requested.
Which visible render units should be mounted.
Whether rows or cells are the optimal memoization unit.
How changes invalidate existing visible units.
How stable row and column identities become React keys.

Conceptually:

function TableGridLayer<TData>({
    source,
    geometry,
}: TableGridLayerProps<TData>) {
    const renderWindow = useRenderWindow(geometry);

    const materializedWindow = useMaterializedWindow({
        source,
        renderWindow,
    });

    return (
        <VisibleGrid
            source={source}
            geometry={geometry}
            window={materializedWindow}
        />
    );
}


The wrapper only sees one component:

<TableGridLayer source={source} geometry={geometry} />


The grid layer may internally contain:

TableGridLayer
├── viewport-window controller
├── loading-demand controller
├── row traversal
├── visible-row descriptors
└── independently rendered rows
    └── independently rendered cells, if needed

Separate rendering overscan from loading buffer

For millions of rows, these should not necessarily be the same range:

interface GridWindows {
    visible: AxisWindow;
    rendered: AxisWindow;
    requested: AxisWindow;
    materialized: AxisWindow;
}


For example:

Visible rows:       1000 to 1030
Rendered rows:       990 to 1040
Materialized rows:   800 to 1300


The grid layer can render 50 rows while keeping a much larger range available through the provider. It should not create React components for every loaded row.

Loaded does not mean rendered.
Rendered does not necessarily mean visible.


That distinction is essential at production scale.

Let the source support demand, not prescribe paging

The grid should preferably express viewport demand without assuming page numbers:

interface GridDemand<RowAnchor, ColumnAnchor> {
    rows: {
        anchor: RowAnchor;
        beforePixels: number;
        afterPixels: number;
    };

    columns: {
        anchor: ColumnAnchor;
        beforePixels: number;
        afterPixels: number;
    };
}


The injected source decides how to fulfill it:

interface PartialGridSource<RowId, ColumnId> {
    traverseRows(
        window: TraversalWindow,
        visitor: (row: VisibleRow<RowId>) => void,
    ): TraversalResult;

    traverseColumns(
        window: TraversalWindow,
        visitor: (
            column: VisibleColumn<ColumnId>,
        ) => void,
    ): TraversalResult;

    requestCoverage(
        demand: GridDemand<unknown, unknown>,
        signal: AbortSignal,
    ): Promise<void>;
}


The source might use pages, cursors, B+ tree leaves, generated data, a database, or something else. Neither SpreadsheetView nor TableGridLayer needs to know.

Fine-grained rendering stays inside the grid layer

Initially, TableGridLayer might use row-level render units:

function VisibleGrid<RowId, ColumnId>({
    rows,
    columns,
    source,
    geometry,
}: VisibleGridProps<RowId, ColumnId>) {
    return (
        <>
            {rows.map(row => (
                <VisibleRow
                    key={row.id}
                    row={row}
                    columns={columns}
                    source={source}
                    geometry={geometry}
                />
            ))}
        </>
    );
}


Each row has an opaque revision:

interface VisibleRow<RowId> {
    id: RowId;
    visibleIndex: number;
    revision: unknown;
}


The row renderer can be memoized based on that revision:

const VisibleRow = React.memo(
    VisibleRowImplementation,
    (previous, next) =>
        previous.row.id === next.row.id &&
        previous.row.revision === next.row.revision &&
        previous.columns === next.columns &&
        previous.geometry.revision ===
            next.geometry.revision &&
        previous.source === next.source,
);


If profiling later shows that one row is still too coarse, VisibleRow may internally render independently subscribed cells. That change does not affect SpreadsheetView or its public API.

This is good encapsulation:

Version 1:
TableGridLayer uses row-level memoization

Version 2:
TableGridLayer uses cell-level subscriptions

SpreadsheetView remains unchanged.

Geometry is a shared service, not a grid implementation detail

One qualification is important: the grid layer may own cell materialization and rendering, but it should not privately own geometry if selection and editing need the same coordinates.

useTableGeometry is therefore a good side integration at the composition level.

                  TableGeometry
                 ↙      ↓       ↘
        TableGridLayer Selection EditBox


All layers consume the same geometry capability:

interface TableGeometry<RowId, ColumnId> {
    readonly revision: number;

    getCellRectangle(
        rowId: RowId,
        columnId: ColumnId,
    ): Rectangle | undefined;

    getRangeRectangles(
        range: SelectionRange<RowId, ColumnId>,
    ): readonly Rectangle[];

    findCellAtContentPoint(
        x: number,
        y: number,
    ): CellAddress<RowId, ColumnId> | undefined;

    getContentExtent(): {
        width: number;
        height: number;
    };
}


This does not mean SpreadsheetView performs geometry calculations itself. It only obtains and distributes the geometry service.

The grid layer uses it to position cells. The selection layer uses it to position range overlays. The edit box uses it to position the editor.

Be careful about what useTableGeometry returns

If the hook returns a new object on every wrapper render:

function useTableGeometry() {
    return {
        getCellRectangle,
        findCellAtPoint,
        contentWidth,
        contentHeight,
    };
}


then memoized layers may see a changed geometry prop every time.

Prefer a stable controller identity:

function useTableGeometry(
    options: GeometryOptions,
): TableGeometryController {
    const controllerRef =
        useRef<TableGeometryController | null>(null);

    if (controllerRef.current === null) {
        controllerRef.current =
            new TableGeometryController(options);
    }

    useLayoutEffect(() => {
        controllerRef.current!.configure(options);
    }, [options.projectionRevision, options.sizingRevision]);

    return controllerRef.current;
}


Or memoize the returned object carefully. The central point is:

Same geometry state
→ same geometry/controller identity

Geometry changed
→ revision changes and relevant subscribers update

useEditBox may belong closer to EditBoxLayer

There is a useful test for hook placement:

Which components actually need the hook’s changing state?

If only EditBoxLayer needs the current draft text and editing mode, put useEditBox inside that layer:

function EditBoxLayer({
    commands,
    geometry,
}: EditBoxLayerProps) {
    const editor = useEditBox({
        commands,
        geometry,
    });

    return <EditBox controller={editor} />;
}


This prevents every keystroke from rerendering the wrapper.

If other layers need only stable edit commands, separate commands from changing editor state:

interface EditCommands {
    begin(address: CellAddress): void;
    cancel(): void;
    commit(): void;
}

interface EditSnapshot {
    address?: CellAddress;
    draft: string;
    phase: "idle" | "editing" | "committing";
}


Then only the edit layer subscribes to EditSnapshot. The pointer interaction layer can call stable commands.

The wrapper should compose capabilities, not snapshots

This distinction is important.

Less desirable:

const geometryState = useTableGeometry();
const editBoxState = useEditBox();
const selectionState = useSelection();

        <SelectionLayer selectionState={selectionState} />
        <EditBoxLayer editBoxState={editBoxState} />

Every changing snapshot causes the wrapper to rerender.

Prefer stable capabilities:

return (

            geometry={geometry}

Each layer subscribes to only the snapshots it needs.

A suitable final boundary
SpreadsheetView
Responsibilities:
- establish viewport
- establish content coordinate space
- connect injected capabilities
- compose layers
- route high-level interaction commands

TableGridLayer
Responsibilities:
- derive visible window
- traverse visible rows and columns
- request partial materialization
- render visible cells
- choose row/cell memoization granularity
- subscribe to cell or row changes
- expose or report measurements to geometry

SelectionRangeLayer
Responsibilities:
- subscribe to logical selection
- subscribe to relevant geometry changes
- derive range rectangles
- render overlays

EditBoxLayer
Responsibilities:
- subscribe to edit-session state
- subscribe to target-cell geometry
- render and position the active editor
- collect draft input
- emit commit/cancel commands

TableGeometry
Responsibilities:
- map logical addresses to content coordinates
- map content coordinates to logical addresses
- manage dimensions and layout revision
- preserve one coordinate system across layers

One caution about “the grid decides everything”

The grid should decide rendering strategy, but it should not decide business semantics.

It may decide:

virtualization window;
overscan size;
row versus cell render units;
cache eviction;
prefetch timing.

It should not decide:

whether deleting rows moves selection to the previous or next row;
whether collapsing a hierarchy preserves hidden selection;
whether an edit participates in undo;
whether a sheet replacement clears history;
how records are persisted.

Those stay in injected controllers or policies.

So yes, your proposed direction is sound:

SpreadsheetView is the composition boundary. TableGridLayer is the rendering and virtualization boundary. The wrapper should not know the number of currently materialized cells or the memoization strategy.

With millions of rows, that encapsulation is not merely stylistic. It allows you to replace the grid’s internal rendering strategy later without changing the headless API, business-data adapter, selection model, or editor layer.

Yes, you are very close, and the separation of responsibilities you describe is good. There is just one important correction:

The subscription listener should normally not modify the business data. A command handler modifies the business data, then the change source notifies subscribers about what changed.

Otherwise, a listener becomes both an observer and a mutation authority, which can produce loops and make behavior depend on whether a UI component is currently mounted.

Two separate directions

Think of the architecture as having a command channel and a notification channel:

UI → command → business model
UI ← change notification ← business model

Command channel

The UI reports the user’s intention:

commands.commitCell({
    rowId,
    columnId,
    value,
});


This command has authority to modify the business data.

Notification channel

After the business model has successfully applied the operation, it reports the result:

changes.publish({
    type: "cell-updated",
    rowId,
    columnId,
});


Subscribers use the notification to invalidate rendering, selection, layout or other derived state. They should not apply the original business mutation again.

Correct flow for editing a cell
1. User types into CellEditor
2. CellEditor owns only the temporary draft
3. User commits
4. CellEditor sends CommitCell command
5. Command handler validates the value
6. Command handler modifies authoritative business data
7. Command handler publishes CellUpdated
8. Relevant rendered cell is notified
9. That cell reads its new value and rerenders
10. Editor closes


In code:

interface SpreadsheetCommands<RowId, ColumnId> {
    commitCell(command: {
        rowId: RowId;
        columnId: ColumnId;
        value: unknown;
    }): void;
}

type SpreadsheetChange<RowId, ColumnId> =
    | {
          type: "cell-updated";
          rowId: RowId;
          columnId: ColumnId;
      }
    | {
          type: "rows-inserted";
          at: number;
          rowIds: readonly RowId[];
      }
    | {
          type: "rows-deleted";
          at: number;
          rowIds: readonly RowId[];
      }
    | {
          type: "columns-inserted";
          at: number;
          columnIds: readonly ColumnId[];
      }
    | {
          type: "columns-deleted";
          at: number;
          columnIds: readonly ColumnId[];
      }
    | {
          type: "projection-reset";
      };

interface SpreadsheetChangeSource<RowId, ColumnId> {
    subscribe(
        listener: (
            change: SpreadsheetChange<RowId, ColumnId>,
        ) => void,
    ): () => void;
}


The command implementation might be:

function commitCell(command: {
    rowId: RowId;
    columnId: ColumnId;
    value: unknown;
}): void {
    businessModel.updateCell(
        command.rowId,
        command.columnId,
        command.value,
    );

    changePublisher.publish({
        type: "cell-updated",
        rowId: command.rowId,
        columnId: command.columnId,
    });
}

What the listener does

A rendering listener receives the notification:

changeSource.subscribe(change => {
    switch (change.type) {
        case "cell-updated":
            invalidateRenderedCell(
                change.rowId,
                change.columnId,
            );
            break;

        case "rows-inserted":
        case "rows-deleted":
            invalidateVisibleRows();
            break;

        case "projection-reset":
            invalidateEntireVisibleWindow();
            break;
    }
});


The important distinction is:

Command handler:
    changes authoritative business data

Subscriber:
    reacts to the completed change


A mounted cell subscriber might simply reread the value:

function handleCellInvalidated(): void {
    const latestDescriptor = source.getCell(
        rowId,
        columnId,
    );

    updateRenderedSnapshot(latestDescriptor);
}


This is a useful combination of push and pull:

Push:
    "Cell 42/amount changed."

Pull:
    "Give me the current value of cell 42/amount."


The notification need not carry the new business value. It only identifies what became stale.

Why the listener should not perform the mutation

Suppose the listener itself updates the business data:

Cell editor publishes "cell changed"
        ↓
Listener updates business data


Several problems appear.

No listener might exist

If TableGridLayer is unmounted, there may be no listener. The business operation would never happen.

There may be multiple listeners

You might eventually have:

the visible grid;
an audit panel;
a formula engine;
a validation system;
a selection controller;
a persistence adapter.

If every listener interprets the event as a command, the mutation could happen more than once.

A listener might subscribe late

Change notifications usually describe completed changes. A newly mounted listener should read the current snapshot, not replay old business commands.

Notification loops become possible
Listener receives event
→ listener changes business model
→ business model emits another event
→ listener receives another event


Therefore, subscriptions are best treated as observation, not authority.

Cell editor responsibility

Your instinct regarding CellEdit is right. It should have a narrow responsibility:

CellEdit
├── display the current editing value
├── maintain the temporary draft
├── handle keyboard and input events
├── request commit or cancellation
└── not know how business data is stored


For example:

interface CellEditProps<RowId, ColumnId> {
    rowId: RowId;
    columnId: ColumnId;
    initialValue: string;

    onCommit(request: {
        rowId: RowId;
        columnId: ColumnId;
        value: string;
    }): void;

    onCancel(): void;
}

function CellEdit<RowId, ColumnId>({
    rowId,
    columnId,
    initialValue,
    onCommit,
    onCancel,
}: CellEditProps<RowId, ColumnId>) {
    const [draft, setDraft] = useState(initialValue);

    return (
        <input
            value={draft}
            onChange={event => {
                setDraft(event.currentTarget.value);
            }}
            onKeyDown={event => {
                if (event.key === "Enter") {
                    onCommit({
                        rowId,
                        columnId,
                        value: draft,
                    });
                }

                if (event.key === "Escape") {
                    onCancel();
                }
            }}
        />
    );
}


CellEdit does not mutate Txn, an AVL tree, a B+ tree or anything else. It emits a semantic request.

Structural operations follow the same flow

Consider inserting a row:

UI requests InsertRows
        ↓
Command handler modifies business structure
        ↓
Command handler records undo information
        ↓
Command handler resolves selection policy
        ↓
Command handler publishes RowsInserted
        ↓
Grid updates visible traversal/layout
        ↓
Selection overlay updates if necessary


The command could be:

commands.insertRows({
    at: 10,
    count: 3,
});


After successfully applying it:

changePublisher.publish({
    type: "rows-inserted",
    at: 10,
    rowIds: insertedRowIds,
});


Different listeners react according to their responsibilities:

TableGridLayer
    → invalidates row traversal and rendered window

TableGeometry
    → inserts three row sizes into its Y-axis model

SelectionController
    → transforms logical selection if required

EditBoxController
    → relocates or cancels the active editor

HistoryController
    → already received the transaction information


However, I would preferably have the transaction controller process model, selection and history atomically, then publish the outcome. The subscribers should not collectively define the business transaction.

A transaction result is even cleaner

Instead of the command handler publishing unrelated notifications as it works, it can produce one completed transaction result:

interface SpreadsheetTransactionResult<
    RowId,
    ColumnId
> {
    changes: readonly SpreadsheetChange<
        RowId,
        ColumnId
    >[];

    selectionEffect?: SelectionEffect<
        RowId,
        ColumnId
    >;

    layoutEffect?: LayoutEffect;
}

function execute(
    command: SpreadsheetCommand,
): SpreadsheetTransactionResult {
    const result = businessModel.apply(command);

    history.record(result.historyEntry);
    selectionController.apply(result.selectionEffect);

    changePublisher.publish(result.changes);

    return result;
}


That prevents the UI from being responsible for coordinating a multi-part mutation.

Authority map

The responsibilities can be summarized like this:

Cell editor
    Authority over:
    - temporary draft
    - commit/cancel intention

Command or transaction handler
    Authority over:
    - business mutation
    - validation
    - undo entry
    - transaction success or failure

Business model
    Authority over:
    - authoritative cell and structural data

Change publisher
    Authority over:
    - announcing completed invalidations

TableGridLayer
    Authority over:
    - visible rendering
    - virtualization
    - rendering cache invalidation
    - partial-load demand

Selection controller
    Authority over:
    - logical selection state
    - selection transformations

TableGeometry
    Authority over:
    - content-space positions and dimensions

EditBoxLayer
    Authority over:
    - editor presentation and temporary draft

The clean final flow
CellEdit
    .onCommit(request)

        ↓

SpreadsheetCommands
    .commitCell(request)

        ↓

BusinessModel
    .updateCell(...)

        ↓

ChangePublisher
    .publish({
        type: "cell-updated",
        rowId,
        columnId,
    })

        ↓

TableGridLayer
    invalidates that mounted cell

        ↓

Cell renderer
    pulls the latest descriptor and rerenders


So your conclusion is essentially correct: this separates the editor from business mutation and allows the grid to update precisely. Just rename the roles mentally:

The editor sends a command describing the requested change.
The command handler has mutation authority.
The subscription mechanism communicates the completed result.
The listener invalidates and rerenders, but does not perform the original business mutation.

That distinction will keep the architecture deterministic and prevent subscriptions from becoming hidden command handlers.
