That's one of the hardest parts of building a spreadsheet. Once rows or columns have variable sizes, you can no longer compute visibility with simple arithmetic like:




const firstRow = Math.floor(scrollTop / rowHeight);




That only works when every row has the same height.



Instead, most spreadsheet and virtualization engines introduce a layout index that stores cumulative positions.



For example, suppose your row heights are:




Row  Height

0    20

1    20

2    50

3    18

4    30




You build a prefix sum of their top positions:




Row  Top   Bottom

0      0      20

1     20      40

2     40      90

3     90     108

4    108     138




Now if the viewport starts at scrollTop = 45, you don't scan every row. Instead, you find the first row whose range contains that position:




45 ∈ [40, 90)




So rendering begins at row 2.



Binary search



Since the Top values are sorted, you can binary search them.




const row = findRowAt(scrollTop);




This is O(log n) instead of O(n).



You do the same for the bottom of the viewport to find the last visible row.





Dynamic row heights



What if a row changes height?




Row 2: 50 → 80




You update the cached positions for the rows after it.



There are several data structures for this:



Recompute the whole prefix array (simple, fine for moderate sizes).

Use a Fenwick tree (Binary Indexed Tree).

Use a segment tree.

Use another balanced tree structure that supports prefix sums efficiently.



Many mature grids use one of the latter approaches because updates become much cheaper.

Widths:




100

150

80

250

0      0     100

1    100     250

2    250     330

3    330     580

Visible rows:

120–145



Visible columns:

3–8

rows × columns

What about really tall cells?



If your rows can become arbitrarily tall because of wrapped text or custom content, you have two common strategies:



Measure lazily. Assume an estimated height until the row is rendered, then measure its actual height and update the layout cache.

Require explicit heights. The model tells the spreadsheet each row's height up front, avoiding runtime measurement.



Many virtualization libraries use the first approach because it's flexible, though it requires handling layout updates when measurements change.

Renderer

It shouldn't know anything about scrolling math or binary searches.





Why not put it in the viewport?



Because viewport is stateful, while layout is structural.



The viewport changes constantly:




scrollTop

scrollLeft

width

height




The layout only changes when the document changes:



row height changes

column width changes

rows inserted/deleted

columns inserted/deleted



Those are different lifecycles.

interface LayoutEngine {

The components receive the current state and notify the outside world about user interactions.



For example:

Cell

    ↓

Spreadsheet

    ↓

    type: "selectCell",

    row,

    column,

})




The state manager updates the selection, and React re-renders with the new state.



This has several advantages:



The spreadsheet is easier to test because its behavior depends on explicit inputs (model and state).

You can serialize and restore state.

Features like undo/redo become much easier if state changes flow through a central mechanism.

The same state could, in principle, be observed by other parts of your application.



I would still distinguish between application state and ephemeral view state.



For example, these are often worth keeping externally:



current selection

active cell

editing state

expanded tree nodes

column widths (if user-configurable)

row heights (if user-configurable)



Whereas some values are implementation details of the renderer:



a reference to a DOM element

whether the mouse is currently inside a particular cell during a pointer event

cached measurements

animation frame IDs



Those don't usually need to live in the external state because they aren't part of the spreadsheet's logical state—they're implementation details.



So I think the guiding principle is:



Logical spreadsheet state (what the user would expect to persist or participate in undo/redo) lives outside the components.

Rendering state (what's needed to draw efficiently or interact with the DOM) can stay inside the renderer.



That keeps your React components relatively thin while allowing the spreadsheet's behavior to be driven by a central state model, which fits well with the architecture you've described.
